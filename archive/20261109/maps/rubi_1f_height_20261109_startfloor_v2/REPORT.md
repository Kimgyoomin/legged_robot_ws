# 시작 방 바닥 보정과 다섯 단차 검증 — 2026-11-09

확인 결과, 6/10/29cm 단차의 높이 정보는 지도에 남아 있다. 단차 우회는 지도에서 단차가 사라져서 생긴 현상이 아니라, 현재 통과 제한과 높이 비용의 영향이다. 사용자에게 확인한 시작 방 `(2.64, 0.12)` 주변의 빈 바닥·이동 물체 흔적은 **별도 v2 지도**로 보정했다. 다만 시작 방에서 복도로 연결되는 경로는 여전히 실패한다. 높이 제한을 모두 제외한 진단에서도 기존 occupancy와 45cm costmap clearance 조합이 출구를 차단한다.

주요 파일:

- `probe.json`, `costmap_connectivity.json`: planner core 비교 및 출구 연결성 진단.

## 2. 시작 방 보정 범위와 결과

사용자는 평탄화할 곳을 시작 방 `(2.64, 0.12)` 주변으로 확인했다. 적용 후보 범위는 map 좌표 `x=0.60~4.45m`, `y=-3.00~1.15m`이며, 이 사각형 전체를 일괄 평탄화한 것은 아니다.

1. 기존 2D occupancy에서 자유 공간이고 구조물과 0.35m 이상 떨어진 후보만 사용했다.
2. 기존 PCD 바닥 비교 결과를 사용해 낮은 바닥 지지점을 골랐다. 앞서 추론·수정한 셀은 바닥 지지점에서 제외했다.
3. 주변 지지점으로 국소 평면을 추정하고, 기존 PCD 바닥과의 차이가 3.5cm 이내인 후보만 채우거나 보정했다.
4. 실제 단차 보호 영역, 구조물 주변 및 지지점이 부족한 미관측 부분은 남겼다.

| 항목 | v1 → v2 변화 |
|---|---:|
| 새로 채운 빈 셀 | 125개, 0.3125m² |
| 평탄화한 기존 관측 셀 | 625개, 1.5625m² |
| 최대 높이 수정량 | 0.615m |
| 국소 바닥 fitting RMS 중앙값 / 95백분위 | 11.75 / 16.98mm |
| 다섯 단차 주변 수정 | 0개 |

누적 원본 대비로는 추론한 바닥 5,295셀, 수정한 관측 662셀이다. 사용 가능한 높이 셀은 원본 258,096개에서 v2 263,391개가 됐다. 다섯 단차의 중심 주변 반경 1.2m 내 높이값은 원본과 동일함을 별도로 검사했다.

![시작 방 보정 전후와 수정 위치](start_before_after.png)

좌측은 v1, 가운데는 v2, 우측은 이번 변경 마스크다. 청록색은 빈 셀 채우기, 주황색은 기존 관측의 높이 보정이다. 빨간 X는 사용자가 지정한 시작점이다.

**해석의 한계:** 새로 채운 값은 실제 재관측이 아니라 주변 바닥에서 추론한 값이다. 사용자가 방 주변의 이동 물체 흔적을 확인했지만 각 셀을 개별 확인한 것은 아니다. RGHM 형식 자체에는 inferred 구분이 없으므로 `provenance.npz`를 함께 보존해야 한다. 새 셀의 variance `0.0009` 및 저장 시각은 파일 표현용 값이며 실측 불확실성이나 새 관측 시각을 의미하지 않는다. 기존 셀에 남긴 variance도 보정 후 오차를 재추정한 값은 아니다.

## 3. 다섯 단차의 높이

지도 해상도는 5cm다. 각 물체 주변 약 0.5~1.0m 고리 영역의 바닥에 강건한 평면 fitting을 적용하고, 이전에 지정한 윗면 영역에서 그 평면을 뺀 상대 높이를 측정했다. 단일 클릭 셀보다 윗면 중앙값을 대표값으로 썼다. 아래 P10~P90은 윗면 셀의 공간적 높이 분포이며 통계적 신뢰구간은 아니다.

|---|---|---:|---:|---:|---:|
| S5 | (19.8271, 43.1609) | 10cm | **10.69cm** | 10.16~11.24cm | 5.91mm |

윗면 측정 셀은 순서대로 30, 30, 12, 36, 20개다. 다섯 물체 모두 의도한 높이에 대응하는 구조가 확인된다. S3의 10cm 단차는 분포가 더 넓어 윗면이 상대적으로 덜 균일하다. 이 데이터만으로 그 원인을 움직임, 센서 오차, 지도 fusion 중 하나로 확정할 수는 없다. 6cm 단차도 데이터에는 있으며, 전체 지도의 넓은 Z 색 범위를 쓰면 RViz에서 눈에 덜 띌 수 있다.

## 4. 작은 단차도 우회하는 이유

현재 `src/legged_bringup/config/planner.yaml`의 주요 값은 다음과 같다. 이번에는 변경하지 않았다.

| 설정 | 값 | 역할 |
|---|---:|---|
| `evaluation.max_crossable_height_jump_m` | 0.10m | 큰 셀 간 높이 변화 통과 제한 |
| `evaluation.local_relief_threshold_m` | 0.10m | 국소 높이 범위에 대한 통과 제한 |
| `evaluation.local_relief_hard_reject_enabled` | true | 위 국소 높이 제한 활성화 |
| `evaluation.grid_terrain_clearance_distance_m` | 0.20m | 위험 지형 주변 여유 거리 |
| `costmap_clearance_m` | 0.45m | occupancy 장애물 여유 거리 |
| `evaluation.height_cost_weight` | 1.0 | 통과 가능한 단차에도 비용 부여 |

`height_noise_floor_m=0.01`은 10cm 통과 한도에 더해주는 1cm 허용 오차가 아니다. 높이 통과 제한과 비용 계산은 구분해야 한다.

- **29cm 두 단차:** 10cm 통과 제한을 넘으므로 우회가 예상되는 동작이다.
- **10cm 두 단차:** 윗면 중앙값만으로 통과를 결정하지 않는다. 검사한 주변에서 국소 높이 범위가 각각 약 11.86cm, 12.07cm까지 나와 일부 경계/중심 통과가 제한되고, 지형 여유 거리도 적용된다. 모든 방향의 모든 셀이 동일하게 막힌다는 뜻은 아니다.
- **6cm 단차:** 검사한 직선 횡단은 통과 가능했다. 그런데 현재 높이 비용 때문에 우회가 더 저렴했다.

6cm 물체를 가로지르는 동일 시작/목표에서, 실제 Nav2 costmap snapshot과 같은 컴파일된 planner core로 비교했다.

| 후보 | 경로 길이 | 누적 비용 |
|---|---:|---:|
| 단차 횡단 직선 | 2.000m | 2.907 |
| 현재 설정의 우회 | 2.290m | **2.351** |
| 진단용으로 높이 비용만 0으로 둔 경우 | 2.000m | 2.000 |

즉, **“넘을 수 있음”과 “넘는 경로가 선택됨”은 다르다.** 현재 CoT 기반 비용표는 예를 들어 5cm에 0.361m, 7cm에 0.716m의 등가 평지 거리 벌점을 부여한다. 실제 누적 비용은 각 이동의 높이 변화와 국소 높이 정보에 따라 계산된다. 높이 비용 0 실험은 원인을 분리하기 위한 진단이며 실제 설정에는 적용하지 않았다.

![현재 경로와 높이 비용을 제외한 진단 경로](step_paths.png)

흰색은 현재 설정, 자홍색은 진단용 높이 비용 0, 빨간 선은 통과 제한 영역 경계다. 단차를 실제보다 낮게 수정해서 경로를 억지로 통과시키지 않았다.

## 5. 시작 방에서 복도로 아직 경로가 연결되지 않는 이유

실제 Nav2 global costmap을 저장해 높이 제한을 전부 제외하고 연결성을 검사했다. 시작 `(2.63946,0.121986)`과 복도 `(8.86457,7.98741)`는 아래와 같았다.

| costmap clearance | 높이 제한을 제외한 연결성 |
|---|---|
| 0.45m, 현재 값 | 연결되지 않음 |
| 0.40m | 연결되지 않음 |
| 0.35m | 연결되지 않음 |
| 0.30m, 진단용 | 연결됨 |

현재 코드의 격자 보수 여유는 `sqrt(2) × resolution`이므로 5cm 격자에서는 45cm 설정에 약 7.1cm가 추가되어 lethal 셀 중심 기준 약 52.1cm를 배제한다. 이것은 추가 로봇 반경을 임의로 더한 분석이 아니라 코드의 거리 확장 방식이다.

![높이 제한 없이 costmap만 본 시작 방 출구](start_costmap_only.png)

따라서 추가 바닥 채우기만으로 현재 출발 경로 문제를 해결할 수 없다. 다음 확인 대상은 **occupancy에 표현된 출입구 폭, 실제 로봇 폭, planner의 costmap clearance 설정**이다. 0.30m 결과는 원인 분리용이며 이 값을 바로 실차 설정으로 권장하는 것은 아니다. 실험 값은 모두 분석 프로세스 안에서만 변경했다.

## 6. 실제 Nav2 검증 결과

ROS domain 187, localhost에서 `mode:=review`, `rviz:=false`, `review_planning_time_ms:=5000`으로 planner만 실행했다. `/cmd_vel`, `/legged/cmd_raw`, `/legged/cmd_safe` 토픽이 없음을 확인했다. 별도로 열린 사용자 review 창과 실차 구동은 건드리지 않았다.

v1에서 다섯 단차 주변의 시작/목표 경로 생성은 모두 성공했다. 이 결과는 주변으로 우회하는 경로의 성공이며 모든 단차를 밟고 통과했다는 뜻이 아니다. 해당 영역은 v2에서도 원본과 동일하다.

설치된 v2 `site.yaml`로 실행한 최종 검증:

| 요청 | 결과 | 소요 시간 |
|---|---|---:|
| 시작 방 (2.64,0.12) → 복도 (8.86,7.99) | 실패: `grid path not found` | 약 0.69s |
| 시작 (2.58,-0.07) → 먼 목표 (48.60,41.46) | 실패: `grid path not found` | 약 0.67s |
| 방 안 다른 시작 (3.52,0.49) → 복도 | 실패: `grid path not found` | 약 0.67s |
| 6cm 주변 (31.475,43.875) → (33.475,43.875) | 성공, 41 poses, 우회 경로 | 약 0.61s |

로그와 좌표 배열은 `audit/final_runtime/`에 있다. 위 시간은 action 호출의 벽시계 시간이며 planner 내부 연산 시간만 뜻하지 않는다. 최종 검증 프로세스는 종료했다. 지도 보정 완료와 전체 출발 경로 성공을 구분해야 한다.

## 7. 새 보정본 열기

기존 review launch를 종료한 뒤 아래 명령으로 실행한다. frozen map review이므로 rosbag이나 실시간 localization은 필요하지 않다. 2D Pose Estimate는 이 모드에서 planner 시작점을 지정한다.

```bash
cd ~/legged_robot_ws
source tools/navigation_env.sh
export ROS_DOMAIN_ID=186
export ROS_LOCALHOST_ONLY=1

ros2 launch legged_bringup rubi_height_navigation.launch.py \
  mode:=review \
  site:="$PWD/maps/rubi_1f_height_20261109_startfloor_v2/site.yaml" \
  review_planning_time_ms:=5000
```

이번 작업으로 추가된 지도·그림·로그만 새 폴더에 저장했다. 이후 실제 단차 통과 정책을 바꾸려면 바닥 보정과 별개로 통과 높이 한도, 국소 높이 제한, 위험 지형 여유 거리, CoT 비용을 함께 검토해야 한다.
