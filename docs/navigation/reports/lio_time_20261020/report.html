Fast-LIO / Nav2 시간 진단

2026-10-20 · ROS domain 45 · 실행 프로세스와 설정을 바꾸지 않고 기록

재실행 후 기록에서는 이전의 지속적인 0.8~1초 지연이 재현되지 않았다. 기록 후반에 시뮬레이션 시간이 59.202초에서 멈췄다. 과거 지연의 시작 원인은 아직 확정하지 않았다.

같은 시각의 점군과 출력 도착 시각 비교

진단 노드가 원시 PointCloud2를 받은 시점부터, 동일 스캔 시각(±1μs)의 출력이 도착할 때까지의 wall-clock 간격. CPU 커널 처리 시간 자체가 아니며 통신·콜백 실행 대기를 포함한다.

출력대응 표본 수중앙값95백분위
/Odometry7020.9 ms90.3 ms
/tf:camera_init->body6621.4 ms90.3 ms
/tf:map->camera_init69135.2 ms678.0 ms

map TF의 지연 상위 표본에는 시뮬레이션 진행이 느려진 구간이 포함된다. 수신 당시 마지막 /clock 값과 메시지 시각 차이는 odometry 약 0.1초, map TF 약 0.2초였다. /clock이 10Hz로 갱신되므로 이 값은 정확한 연산 지연과 같지 않다.

현재 입력 및 정지 상태

  • 측정한 CustomMsg 57개에서 offset_time 최솟값·최댓값이 모두 0, timebase는 스캔 헤더 시각과 일치했다. 현재 시뮬레이터의 순간 스캔 모델이며, 실제 Livox의 점별 시각을 0으로 바꾸라는 의미가 아니다.
  • 관측된 입력·출력 타임스탬프 역행 없음.
  • Fast-LIO 실행 파라미터: use_sim_time=true, time_sync_en=false, time_offset_lidar_to_imu=0.0.
  • 20초 기록 중 /clock은 52.202→59.202초까지 진행한 뒤 중단. 후속 4초 확인에서는 clock·costmap 새 메시지가 없고 최종 명령 게이트는 collision_cloud_timeout이었다.
  • 71개 원시 점군에 대해 원래 타임스탬프로 TF를 기다렸을 때 68개 변환 성공. 마지막 3개는 시뮬레이션 정지 구간에 걸려 대기 제한에 도달했다. 미래 TF 사용이나 타임스탬프 덮어쓰기는 하지 않았다.

오류 문구를 해석할 때의 주의점

설치된 Humble message_filter.h의 transformReadyCallback은 future.get()의 예외를 모두 OutTheBack으로 분류한다. 따라서 “timestamp … earlier than … transform cache”는 과거 시각이나 clock reset을 단독으로 입증하지 않는다. TF 대기 시간 초과도 같은 문구로 보일 수 있다. 현재 costmap의 TF 대기 설정은 0.6초이므로, 이전에 관측한 0.8~1초 TF 지연은 관측 누락을 설명할 수 있지만 지연 발생 원인은 별도 확인이 필요하다.

공식 코드: Humble TF message filter, Humble obstacle layer.

기각한 단순 가설과 다음 확인

“10Hz clock에 50ms ROS 타이머를 쓰면 반드시 스캔을 10Hz로만 처리한다”는 단순 가설은 domain 147의 독립 실험에서 재현되지 않았다. 29회 clock 갱신에 타이머 58회가 실행되어 초기 대기열 8개가 모두 처리됐다. 따라서 이 이유만으로 Fast-LIO 타이머를 교체하지 않았다.

다음 재생 구간에서 지속적인 지연이 다시 발생하는 경우, 동일 기록과 Fast-LIO 내부 LiDAR/IMU 대기열 계측을 함께 해야 한다. 장애물 후 목표 실패 종료와 재시도 흐름은 별도 미해결 항목이다. 이번 진단에서는 실제 navigation 설정·코드·목표·속도 명령을 변경하지 않았다.
